### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Verify each PR independently before it lands.** Use the GitHub CLI (`gh`). Never require Graphite (`gt`). One background verifier per PR, each in its own git worktree, runs the change the way a user would with the matching control skill (such as `control-ui` or `control-cli` from `cursor-team-kit`), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts. Green CI and an approving bot review are not verdicts.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits. One whose branch neither holds nor needs that code can move onto trunk and land on its own, but needs a fresh verdict against trunk first.
3. **Re-check that verdicts still describe the code.** Record the verdict head SHA, base SHA, and stable `git patch-id` of that PR's base-to-head diff. Compare the recorded patch-id with the current base-to-head patch-id before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files. The change itself still gets fresh checks and a review. A lane with no build output, such as a dev server, cannot show this, so rerun it. Re-verify anything else that drifted. Even with an unchanged patch-id, mergeability and CI must pass at the current head.
4. **Prepare and land only the bottom PR.** Fetch trunk, move the lowest verified PR's patch onto the current trunk when needed, push with `--force-with-lease`, and retarget only that PR with `gh pr edit <pr> --base <trunk>`. Re-run step 3 after any push. Merge with `gh pr merge <pr> --squash`. Arm `--auto` only when the user asked for merge-when-ready and the verdict covers the current head. Read back `gh pr view <pr> --json state,mergedAt,baseRefName,mergeStateStatus,statusCheckRollup,autoMergeRequest`. A requested auto-merge is not a merge. Confirm that the PR is merged with trunk as its base before preparing its child. A stacked PR merged into its parent's branch did not land on trunk.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only branch or base change. Watch the current bottom with `gh pr checks <pr> --watch` as an event wake, then re-read its state until `mergedAt` is non-null or `state` is `MERGED`. Hold the watch with a wake loop (Autonomous run step 2). `autoMergeRequest` is not stack readiness, and `BLOCKED` while checks are pending or auto-merge is armed is not failure. After each confirmed merge, fetch trunk, confirm the merged SHA, remove that PR from the bottom-to-top list, and inspect the next PR's base, head, checks, and patch-id. Do not assume the host retargeted it. If a merge stalls, diagnose before mutating.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you armed, what landed and how you confirmed it, and what the next gap needs.
